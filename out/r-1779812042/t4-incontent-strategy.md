# In-Content Image & Diagram Strategy — WhatIs.site

**Prepared by:** In-Content Image Strategist · run r-1779812042 / t4
**Scope:** 1,620 articles, `src/content/articles/*.md`. Today every article ships with a hero image and **zero** in-body visuals (verified: no `![...](...)` markdown image syntax exists anywhere in the corpus). This plan defines what to add, where first, how to embed it in Astro, and how a solo operator rolls it out.

The core constraint that shapes everything below: this is a zero-JS, build-time, markdown-content site. Every visual must be a static asset referenced from markdown — no lightboxes, no carousels, no client-side diagram libraries. A diagram here is just a `.webp` or `.svg` file under `public/images/articles/`.

---

## 1. Visual types — what fits, what to avoid

These are educational "What Is X?" explainers. The reader arrived confused about a concept and wants it made concrete. That filters the visual types hard.

**Use these (high comprehension value):**

- **Labeled illustrations** — a single object with parts called out. The `aerodynamics` article describes "the four forces that govern flight"; one labeled airfoil with lift/drag/thrust/weight arrows does more than three paragraphs. Same for `anatomy`, `acupressure` (meridian/pressure-point map), `aircraft-mechanics`.
- **Process / flow diagrams** — left-to-right or top-down step sequences. `algorithms` walks through merge sort and binary search; a divide-and-conquer split diagram is the canonical explainer for it. Fits any "how X works" section.
- **Comparison visuals** — two-up side-by-side or a labeled matrix. `acupressure` vs `acupuncture`, bubble sort vs quick sort, P vs NP. The reader's literal question is often "how is A different from B."
- **Conceptual diagrams** — graphs/networks/relationships. `algorithms` describes graphs as "nodes connected by edges"; a tiny node-edge sketch lands instantly.
- **Timelines** — for history-category and "origins" sections (`algorithms` opens with al-Khwarizmi → Euclid → Knuth).

**Avoid:**

- **Decorative stock filler** — a photo of a laptop on an algorithms page adds nothing and dilutes image-search relevance.
- **Text-heavy infographics generated by AI** — diffusion models render letters, numbers, and equation glyphs as garbled nonsense. This is the single biggest failure mode for this corpus and it's mandatory to respect the artifact-safe rules in the **prompt-engineering playbook** (`out/r-1779812042/t3-prompt-playbook.md`): no text, no letters, no numbers in AI-generated images. Any visual whose value *depends* on legible labels must be authored as **SVG/vector**, not generated.
- **Charts with fabricated data** — a bar chart implies a real dataset. Don't manufacture one. Cite a real source or skip it.
- **Screenshots** — versioning and UI drift make them a maintenance trap at 1,620 articles.

## 2. Where to apply first — prioritization

Do not retrofit 1,620 articles. Sequence by leverage: tier (depth/dwell), category (visual-friendliness and traffic potential), and per-article position.

**Images per article by tier** (target the *first* in-body visual near the top, where it lifts dwell and gives image-search a strong, on-topic asset):

| Tier | Word count | In-content visuals | Rationale |
|------|-----------|--------------------|-----------|
| 1 | 3,000–5,000 | 2–3 | Long, scrollable; visuals break the wall of text and earn image-search real estate. 535 articles. |
| 2 | 2,000–3,000 | 1–2 | One strong concept diagram per piece. 269 articles. |
| 3 | 1,200–2,000 | 0–1 | Optional single diagram only where the concept is inherently visual. 808 articles — too many to force. |

**Category priority** (counts from `data/topics-master.json`):

1. **Science (245) + Technology (193)** — first wave. Highest density of inherently diagrammable concepts (forces, processes, graphs, systems) and strong image-search/GEO upside. Mostly tier 1.
2. **Health & Wellness (91) + Sports (85)** — anatomy, body mechanics, technique illustrations; high commercial/traffic value.
3. **History (148)** — timelines and labeled maps/artifacts.
4. **Everyday-concepts (429)** — largest bucket but most variable; only the genuinely visual ones (e.g. how-something-works topics). Cherry-pick, don't blanket.
5. **Arts & Culture (246), Finance (57), Philosophy (34), remainder** — selective, concept-by-concept.

**Phase-1 target:** ~150 articles = tier-1 Science + Technology with an obviously diagrammable core concept. That's the highest comprehension-per-hour-of-work return and a clean pilot to measure dwell-time lift before scaling.

## 3. Implementation in Astro

The mechanics are deliberately boring, which is correct for a zero-JS build-time site.

**Embedding.** Drop the asset under `public/images/articles/` using a `{slug}-fig{n}` convention (e.g. `aerodynamics-fig1.webp`), then reference it in the markdown body with standard syntax placed right after the relevant `##` section opener:

```markdown
![Airfoil cross-section with lift, drag, thrust, and weight force arrows labeled around it](/images/articles/aerodynamics-fig1.webp)
```

Astro renders this through `@tailwindcss/typography`, so it lands inside the existing `.prose prose-lg` wrapper around `<slot />` in `ArticleLayout.astro` — no layout change required. Prose already styles `img` with sensible max-width and margins.

**Alt text is mandatory and is the SEO/GEO payload.** Every figure needs descriptive, specific alt text (the example above, not "diagram"). It serves accessibility, Google Images ranking, and AI-engine comprehension. This mirrors the heroAlt discipline the corpus already follows.

**CLS / dimensions.** The hero is the LCP element and is preloaded — do **not** let in-content images compete. Two rules:
- Always know intrinsic dimensions. Markdown `![]()` doesn't emit width/height, which risks layout shift. The clean fix is the shared component below; the lightweight fallback is to export every figure at a fixed canvas (recommend **1200×675**, matching the hero aspect) and add a `prose img { aspect-ratio: 16/9; }`-style rule so the browser reserves space.
- All in-content images get `loading="lazy"` and `decoding="async"` — they're below the fold by definition, so they must never block LCP.

**Shared figure/caption component — worth it.** Add a tiny `src/components/Figure.astro` that takes `src`, `alt`, `caption`, `width`, `height` and emits a semantic `<figure>` with explicit dimensions, `loading="lazy"`, `decoding="async"`, and a styled `<figcaption>`. This guarantees zero CLS, enables real captions (captions get read and improve dwell + GEO context), and gives one place to later add WebP variants. It can be used in `.md` only if articles are `.mdx`; since the corpus is `.md`, keep plain markdown `![]()` for the body and reserve the component for any future MDX migration — but ship the global `prose img` CSS rule now regardless. Net: build the CSS rule today, the component is a nice-to-have for later.

## 4. Production approach & rollout

**AI-generated (cheap, fast) — must follow the artifact-safe prompt rules.** Labeled-illustration *bases* and conceptual scenes can be generated, but only the wordless imagery. Per the prompt-engineering playbook (`out/r-1779812042/t3-prompt-playbook.md`): no text, letters, numbers, equations, or UI. Generate the airfoil shape, the neuron, the wave, the anatomical form — then add labels and arrows yourself as a vector overlay. Anything where the *meaning lives in the labels* is not an AI-only job.

**Real vector / SVG (manual) — required for:** flow diagrams, comparison matrices, timelines, node-edge graphs, and any labeled illustration. Author in a vector tool or hand-write SVG; export to `.svg` (crisp, tiny, no artifacts) or `.webp` at 1200×675. SVG is preferred for diagrams — sharp at any zoom and often <10 KB.

**Phased rollout (solo operator, rough effort):**

| Phase | Work | Effort |
|-------|------|--------|
| 0 — Plumbing | Add `prose img` CSS (dimensions/aspect-ratio), confirm lazy-loading, optionally scaffold `Figure.astro`. | ~half a day, one-time |
| 1 — Pilot (~50) | Tier-1 Science + Tech "marquee" articles, 1 diagram each. Measure dwell + Google Images impressions via the GSC tooling in `scripts/seo/`. | ~1–2 weeks part-time |
| 2 — Scale wave 1 (~150) | Remaining tier-1 Science + Tech, 2–3 visuals on the longest. | ~3–4 weeks |
| 3 — Wave 2 (~250) | Health/Wellness, Sports, History (timelines), tier-1 + strong tier-2. | ongoing |
| 4 — Long tail | Selective tier-2/3 across remaining categories, only where inherently visual. | as capacity allows |

**Throughput note for one person:** a clean AI-base-plus-vector-label figure runs ~20–40 min once a per-category template exists. Build reusable label/arrow styles in phase 1 so phases 2–4 are mostly content swaps, not redesigns. Don't let "every article needs images" become the goal — a great diagram on 400 high-traffic articles beats a mediocre one on all 1,620.
